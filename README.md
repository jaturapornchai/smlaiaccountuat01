## Objective
ทดสอบระบบ SML AI Account แบบ UAT กับของจริง (ไม่มีผลจำลอง) โดยรันสคริปต์ทีละขั้นตอนที่เขียนไว้ ตรวจได้ทั้งหน้าจอ, API และแถวใน PostgreSQL ของฐาน Demo
รอบที่ไม่ผ่านจะให้สมอง AI (Ollama Cloud) วิเคราะห์ แล้วเปิด issue ใน IssueMate (โปรเจกต์ SMLAIACC) ให้ทีมแก้โปรแกรมต่อ

- ตัว Tester อยู่ที่ https://uat.smlwork.com และทดสอบเว็บ https://www.smlwork.com (เข้าแบบ Demo / ฐาน `smldemo`)
- AI ที่เขียนโปรแกรม (Claude, Antigravity บนเครื่องลุงจืด) สั่งงานผ่าน MCP วงจรคือ
  1. AI สั่งตรวจ → Tester รันกับของจริง
  2. ไม่ผ่าน → เปิด issue ใน IssueMate · ขั้นที่ทำซ้ำแล้วข้อมูลไม่เปลี่ยน (ตรวจ/อ่าน/เปิดจอ/กรอก/เลือก/PDF/`db.query`/`api.request` GET) ล้มแล้วลองซ้ำอีกสูงสุด 2 ครั้ง ห่างกัน 3 วินาที — ผ่านตอนลองซ้ำ = ป้าย "ผ่านเมื่อลองซ้ำ" (flaky) ไม่นับเป็นบั๊ก (`attempt` ใน `runner/run.mjs`) · ยกเว้นทุกขั้นที่พัง (ไม่นับเก็บกวาด) พังเพราะตัวสคริปต์เอง: `psql ผิดพลาด`, `ไม่มีตัวแปร {{…}}`, `AI ทำไม่จบใน N ตา`, ขั้นเตรียมข้อมูล `db.query` ได้ 0 แถวก่อนแตะ ERP, `api.request` ได้ 404 หน้า HTML/405/400 "กรุณาระบุ…", เปิดเมนูที่ไม่มีใน ERP → ไม่เปิด issue แต่บันทึกเหตุการณ์ในบอท และขึ้นเหตุผลบนการ์ดบอท/หน้ารอบ (`noIssue`) ให้แก้สคริปต์ (`scriptFault` ใน `src/lib/script-fault.ts`, ตัวตรวจ `node scripts/check-script-fault.mjs`, รอบตรวจซ้ำของ issue ยังส่งผลเสมอ) · สคริปต์ที่ AI เขียน (`ask-*`, `auto-*` ที่ AI เสนอเอง และที่บันทึกผ่าน MCP `save_script` ซึ่งไฟล์มี `"ai": true`) ผ่านด่าน AI ก่อน (`aiTriage`): ชี้ชัดว่าสคริปต์ผิดเอง → ไม่เปิด issue แต่กดส่งเองได้, ระบบผิด/ไม่แน่ใจ → เปิดตามเดิม · สคริปต์ AI ที่ชี้ว่าผิดเอง AI จะซ่อมให้ (`healScript` ใน `src/lib/command.ts`): เขียนฉบับแก้ลง `runs/<รอบ>/heal.json` ผ่านตัวตรวจเดียวกับ `save_script` แล้วรันลองจากไฟล์นั้น (รายการรอบมีป้าย "AI ซ่อม") — รอบลองผ่านหรือไปถึงจุดที่ ERP ผิดจริงจึงบันทึกทับสคริปต์เดิม (`promoteHeal`), ซ่อมไม่ได้หรือรอบลองยังพังเอง = ไม่ซ่อมต่อ และถ้าเป็น `auto-*` ปลดสคริปต์ออกจากคลังเอง (ย้ายไป `uat-scripts/retired/` ย้ายกลับมาก็ใช้ได้อีก, `retireRun` ใน `src/lib/uat-runs.ts`) (ตัวตรวจ `node scripts/check-heal.mjs`) · สั่งส่งเองได้ด้วย MCP `runs {id, action:"issue"}`
  3. AI แก้โค้ด แล้วสั่งตรวจซ้ำด้วยเลข issue · หรือเปิดสวิตช์ `autoRetest` ให้ Tester ตรวจซ้ำเองเมื่อ ticket ที่มันเปิดเป็น `deployed`
  4. ผ่าน → Tester เขียนคอมเมนต์ปิดวงจรใน issue นั้น (ไม่ผ่าน → คอมเมนต์ว่ายังพังขั้นไหน)
- Zero-touch (ไม่ต้องมีคนกด): ตัวรันขัดข้อง/เกินเวลารวม → ลองรันใหม่เอง 1 ครั้ง (รอบใหม่มี `retryOf`, สรุปรอบกลางคืนนับเฉพาะรอบที่ลองใหม่) · ทุกครั้งที่เซิร์ฟเวอร์เริ่ม (`rerunStranded` เรียกจาก `src/instrumentation.ts`, log `rerun-stranded`) ดูรอบล่าสุดของแต่ละสคริปต์: ไม่ผ่าน/ขัดข้องแต่ไม่มี ticket และไม่มีเหตุผลจากกฎหรือ AI (รีสตาร์ตกลางด่าน AI หรือระหว่างส่ง, ส่ง IssueMate ไม่สำเร็จ, ลองใหม่แล้วยังขัดข้อง) → รันใหม่ให้ผลเข้าด่านเปิด ticket ตามปกติ, `auto-*` ที่ยังพังเอง → ปลดออกจากคลัง · ทำเฉพาะตอนเปิด `autoIssueMate` (ตัวตรวจ `node scripts/check-rerun-stranded.mjs`)
- บทบาทของ AI (ทั้งสมองบอทและคำแนะนำใน MCP): คนไทย เป็นผู้ใช้ทั่วไปของ SML AI Account ที่ทำงานแบบผู้ใช้จริง และเก่ง query กับ data model ตรวจฐานข้อมูลและ flow งานได้ (เช่น ใบเสนอราคา → ใบสั่งขาย → ใบขาย → ภาษีขาย → GL → สต็อก)

ฝูงบอทมี 32 ตัว = 10 โมดูล × 3 มุมตรวจ + เงินสด/ธนาคาร 2 มุม (หน้าจอ ฐานข้อมูล — ยังไม่มีมุม API)
- โมดูล: master, sales, purchase, inventory, gl, tax, reports, security, admin, recon
- มุมตรวจ: หน้าจอ (screen), ฐานข้อมูล (data), API (api)

ข้อมูลบอทอยู่ใน `src/lib/swarm-data.ts`

## Workflow

ข้างในการรันสคริปต์ 1 รอบ:

![ภาพที่ 3 การรันสคริปต์ 1 รอบ](public/guide/3-run.webp)

1. กด ▶ ที่บอท/สคริปต์ หรือ "รันทุกสคริปต์" → เข้าคิว (`src/lib/uat-runs.ts`) รันพร้อมกันตาม "รันพร้อมกันสูงสุด"
2. แต่ละรอบเรียก `node runner/run.mjs --script <ไฟล์> --out runs/<id> --base <เว็บ ERP>` ซึ่งใช้ Playwright เปิดเว็บและใช้ psql ตรวจฐานข้อมูล
   - ตัวรันพิมพ์ผลทีละบรรทัด (JSON) → หน้าจอแสดงไทม์ไลน์ขั้นตอน ค่าที่คาดหวังเทียบค่าจริง และภาพหลักฐาน
   - ขั้น `cleanup` รันเสมอแม้ขั้นหลักพัง
   - หลังทุกขั้นที่เป็นหน้าจอ (`ui.*`) ตัวรันเขียนทับภาพ `runs/<id>/live.jpg` → การ์ดบอทบนหน้าแรกโชว์จอสดว่ากำลังทำอะไร (การ์ดเรียงบอทที่กำลังรันก่อน แล้วตามเวลาทำงานล่าสุด, `src/components/BotCard.tsx`)
   - ขั้นที่ไม่มีหน้าจอ (`db.*`, `api.request`, `report.pdf`) ตัวรันส่งคำสั่งจริงที่เติมตัวแปรแล้ว (`query`, ตัดที่ 600 ตัว ปิดค่าลับ) · issue ที่เปิดก็แนบคำสั่งนี้ไปด้วย
   - การ์ดเล่ารอบล่าสุดของบอทรอบเดียว (ภาพ คำสั่ง ข้อความบนจอ และการกดดูขั้นตอนมาจากรอบเดียวกัน ไม่หยิบภาพรอบเก่า): เลือกขั้นที่จะเล่า = ขณะรันคือขั้นที่กำลังทำ, จบแล้วคือขั้นที่ไม่ผ่าน หรือขั้นสุดท้ายที่รันจริง (ไม่นับเก็บกวาด) → ขั้นนั้นมีคำสั่ง SQL/API ก็โชว์คำสั่ง ไม่งั้นโชว์ `live.jpg` ของรอบนั้น · ข้อความล่างจอ เช่น "ไม่ผ่านขั้น 8/12 · …" นับเป็นขั้น ส่วนแถวล่างการ์ด "ผ่าน 4 รอบ · ไม่ผ่าน 1 รอบ" นับเป็นรอบ
   - ปุ่มขยายจอ (มุมขวาบนของจอการ์ด ข้างเวลา) → จอเดียวกันขยายเต็มหน้าแบบแอนิเมชันซูมออกจากตำแหน่งการ์ด เห็นภาพทั้งจอไม่ครอป/เลื่อนอ่านคำสั่ง SQL ยาวได้ และยังอัปเดตสดขณะรัน · ปิดด้วย Esc, ปุ่ม X หรือคลิกพื้นหลัง (หดกลับเข้าการ์ด)
3. ผลถาวรเก็บที่ `runs/<id>/run.json` พร้อมไฟล์หลักฐาน `NNN-*.png|json|pdf`
   - รอบที่ไม่ผ่านหรือผิดพลาดมีไฟล์เพิ่ม 2 ไฟล์ (`runner/run.mjs` `startRecording`/`stopRecording`):
     - `video.webm`: วิดีโอทั้งรอบ กว้าง 1280 px ที่ 5 fps อัดด้วย `page.screencast` ของ Playwright 1.64 จึงอัดแท็บของ Stagehand ที่ต่อผ่าน CDP ได้ด้วย
     - `trace.zip`: Playwright trace (DOM ทุกขั้น, network, console) เปิดดูทีละคลิกด้วย https://trace.playwright.dev หรือ `npx playwright show-trace trace.zip`
   - รอบที่ผ่าน ตัวรันลบทั้งสองไฟล์ทิ้ง ประหยัดดิสก์
   - หน้ารอบ (`src/components/RunPanel.tsx`) เล่นวิดีโอได้ทันทีและมีปุ่มดาวน์โหลด trace · issue ใน IssueMate และคอมเมนต์รอบที่ยังไม่ผ่านมีลิงก์ทั้งสองไฟล์ (`src/lib/issuemate.ts`)
4. ถ้ารอบนั้น **ไม่ผ่าน** และเปิด "ส่งเข้า IssueMate อัตโนมัติ" ไว้ (`src/lib/issuemate.ts`):
   1. สมอง AI อ่านขั้นที่พังพร้อมภาพหน้าจอ แล้วเขียนบทวิเคราะห์ (เป็นการคาดเดา ต้องตรวจโค้ดจริง)
   2. ระบบเรียก `create_issue` ผ่าน MCP ของ IssueMate โดยตั้งระดับความสำคัญตามระดับปัญหา: S1→critical, S2→high, S3→medium, S4→low
   3. issue ที่สร้างมีขั้นตอนทำซ้ำ บทวิเคราะห์ ภาพหน้าจอ และ run.json แนบไปด้วย
   4. กันส่งซ้ำด้วย `runs/issuemate-sent.json`: สคริปต์เดียว = issue เดียว ถ้ารอบใหม่พังที่ขั้นอื่นจะต่อท้ายผลใน issue เดิม — เมื่อสคริปต์นั้นกลับมาผ่าน ระบบล้างรายการของสคริปต์นั้นเองและคอมเมนต์ใน issue เดิมว่าตรวจซ้ำผ่านแล้ว
   5. รอบที่ผิดพลาด (error) ไม่ส่งอัตโนมัติ ต้องกดส่งเองในแผง "รอบการรัน"
   6. ตรวจซ้ำอัตโนมัติเมื่อแก้เสร็จ (`src/lib/auto-retest.ts`, ตั้งเวลาใน `src/instrumentation.ts`, เปิดที่หน้าตั้งค่า "เรื่องที่แก้เสร็จ (deployed) ใน IssueMate ให้ตรวจซ้ำอัตโนมัติ" ปิดด้วย `UAT_AUTO_RETEST=0`): IssueMate ไม่มี webhook จึงถาม `list_issues` (status `deployed`, ค้น `uat-scripts/`) ทุก 5 นาที → คัดเฉพาะ ticket ที่ Tester เปิดเอง (reporter ขึ้นต้น `UAT Tester Swarm` + บรรทัด `สคริปต์: uat-scripts/<id>.json` ใน description) → `startRuns([id], <เลข ticket>)` แล้ว `closeLoop` / `sendToIssueMate` คอมเมนต์ผลใน ticket เดิมเหมือนสั่งตรวจซ้ำเอง · กันสั่งซ้ำด้วย `runs/auto-retest.json` (เลข ticket → `closedAt` ของรอบ deploy) ถ้าเปิดกลับมาแก้แล้ว deploy ใหม่จะตรวจอีกรอบ · สคริปต์ถูกลบไปแล้ว = ลงฟีดกิจกรรมครั้งเดียว ไม่สั่งวน
5. "สั่งงานตรวจ" (ปุ่มบนแถบบน, ✨ ที่บอท, MCP tool `command`) — `src/lib/command.ts`
   1. ผู้ดูแลพิมพ์ว่าจะให้ตรวจอะไร ไม่เลือกบอท = สมอง AI เลือกบอทที่เกี่ยวเอง (ไม่เกิน 6 ตัว) · ปุ่มบนแถบบนตอบรับทันทีแล้วทำเบื้องหลัง ผลหรือสาเหตุที่ทำไม่ได้ขึ้นฟีดกิจกรรม ("ระบบสั่งงาน") และลง log
   2. แต่ละบอทเขียนสคริปต์ `ask-<โมดูล>-<มุมตรวจ>` จากคอลัมน์จริงใน PostgreSQL แล้วบันทึกผ่านตัวตรวจเดียวกับ `save_script`
   3. สคริปต์จากคำสั่งอ่านอย่างเดียว: ห้าม `db.exec`, ห้าม `ui.adminLogin`, `api.request` ใช้ GET เท่านั้น · SQL ทุกขั้น `db.query` ถูกลอง `EXPLAIN` กับฐาน Demo ก่อนบันทึก (ไม่รันจริง) ถ้าอ้างตาราง/คอลัมน์ที่ไม่มีจริงให้ AI แก้ใหม่ · ใช้ตัวแปร `{{x}}` ที่ไม่มีขั้นก่อนหน้า save/as/set ไว้ก็ตีกลับให้แก้ (`varGuard`) · ถ้าคำสั่งพูดถึงตารางที่มี `trans_flag` AI จะได้รายชื่อเลข=ประเภทเอกสารจริงจากฟังก์ชัน `trans_flag()` ของ SML ไม่ต้องเดา ไม่ปล่อยไปรันพังแล้วเปิด issue ผิดตัว · รอบที่ไม่ผ่านยังเปิด IssueMate ตาม `autoIssueMate` พร้อมหมายเหตุให้ตรวจสคริปต์ก่อน
   4. เข้าคิวรันจริงทันที · รอบที่ไม่ผ่านผ่านด่าน AI ก่อน (ดูการเปิด issue ด้านบน) แล้วเปิด issue ใน IssueMate อัตโนมัติ (issue ของ `ask-*` มีหมายเหตุให้ตรวจสคริปต์ก่อน)
   5. AI คิดเรื่องทดสอบเพิ่มเอง (on the fly, `proposeScripts`): จบแต่ละชุดทดสอบ สมอง AI ดูผลชุดนั้นกับรายชื่อสคริปต์ที่มี แล้วเสนอไม่เกิน 2 เรื่อง (ขุดต่อจากขั้นที่พัง หรือเรื่องที่ยังไม่มีสคริปต์ตรวจ) → บอทที่ตรงเขียนสคริปต์ `auto-<โมดูล>-<เวลา>` ผ่านตัวตรวจเดียวกับข้อ 3 แล้วเข้าคิวรัน · ชุดที่มีแต่ `auto-*` ไม่เสนอต่อ (ไม่วน) · มี `auto-*` ครบ 30 ไฟล์แล้วหยุดเสนอจนกว่าจะลบ/คัดเข้าคลัง · ปิดได้ที่หน้าตั้งค่า หรือ `UAT_AUTO_SCRIPTS=0`

6. คำสั่งผ่าน MCP (`src/app/api/mcp/route.ts`, `src/lib/mcp.ts`)
   - ปลายทาง `POST /api/mcp` (JSON-RPC) รองรับ MCP 2026-07-28 และ 2025-11-25 / 2025-06-18 / 2025-03-26
   - ยืนยันตัวด้วย `Authorization: Bearer <UAT_MCP_TOKEN>`
   - tools 11 ตัว (คำอธิบายเป็นอังกฤษสั้น ผลลัพธ์เป็นบรรทัดสั้น เพื่อประหยัด token):

     | tool | ใช้ทำอะไร |
     |---|---|
     | `status` | สุขภาพระบบ ค่าตั้ง จำนวนสคริปต์ รอบที่กำลังรัน (`bots:true` = ดูรายบอท) |
     | `scripts` | รายการสคริปต์ หรืออ่านไฟล์สคริปต์ตาม `id` |
     | `save_script` | เพิ่ม/แก้สคริปต์ (ตรวจรูปแบบ ตัวแปร `{{…}}` และตาราง/คอลัมน์ SQL ก่อนบันทึก · ติด `"ai": true` = สคริปต์ AI) |
     | `run` | สั่งรันตาม `scriptIds` / `botIds` / `modules` / `all` หรือ `issue` (ตรวจซ้ำสคริปต์ที่เคยเปิด issue นั้น) แล้วรอผลได้ถึง `wait` วินาที (ค่าเริ่มต้น 90) |
     | `runs` | ดูรอบการรัน / ผลละเอียด / หยุด (`action:"stop"`) / ส่งเข้า IssueMate (`action:"issue"`) |
     | `events` | ฟีดเหตุการณ์แบบรอได้ (long-poll) ส่ง `after` = cursor ครั้งก่อน |
     | `logs` | บันทึกการทำงานถาวรของตัวทดสอบเอง (สมอง AI, ค้นเว็บ, ทุก MCP call, ผลรัน, error ของ API, รีสตาร์ท) พร้อมสรุปต่อวัน: จำนวน/ล้ม/เวลาเฉลี่ย-สูงสุด, error ที่เจอบ่อย, งานที่ช้าที่สุด — กรอง `date` `kind` `q` `errors` `limit` |
     | `nightly` | สรุปรอบ regression กลางคืน (ผ่าน/ล้ม/ข้าม ล้มใหม่-หายแล้วเทียบคืนก่อน พร้อมเลข ticket) — ไม่ใส่ `date` = คืนล่าสุด (ดูข้อ 11 ใน Workflow) |
     | `notify` | ส่งข้อความขึ้นหน้าเว็บ |
     | `test_db` | ฐานทดสอบส่วนตัวของ AI: `create` คัดลอก smldemo เป็น `uat_<ชื่อ>` (ไม่กี่วินาที สูงสุด 5 ฐาน) แล้วใช้ `database:"uat_<ชื่อ>"` ในขั้น `db.*` แก้ข้อมูลได้อิสระ · `list` · `drop` (ลบได้เฉพาะฐานที่สร้างจาก tool นี้) |
     | `command` | สั่งงานตรวจเป็นภาษาไทย (`text`, เลือก `botIds` ได้) → AI กระจายงาน เขียนสคริปต์ แล้วรันจริง |

   - ฝั่ง IssueMate ระบบแค่คอมเมนต์ (`converse_on_issue`) ไม่เปลี่ยนสถานะ issue

11. รอบ regression กลางคืน + สรุปเช้า (`src/lib/nightly.ts` ตรรกะ, `src/lib/nightly-run.ts` ต่อสายกับระบบจริง, `GET /api/nightly`, MCP `nightly`, การ์ด "สรุปรอบกลางคืน" ที่หน้าหลัก `src/components/NightlyCard.tsx`)
    - เปิดที่ปุ่มตั้งค่า → "รอบ regression กลางคืน" (ค่าเริ่มต้น **ปิด**) ตั้งเวลาเริ่มเป็น HH:MM เวลาไทย (ค่าเริ่มต้น 02:00)
    - ตัวตั้งเวลาเป็น `setInterval` 30 วินาทีในโปรเซสของเว็บเอง เริ่มจาก `src/instrumentation.ts` — ไม่เพิ่ม unit บนเซิร์ฟเวอร์ และไม่ต้องมี token ไปยิง POST (POST ต้อง Google login) · รีสตาร์ทแล้วตัวตั้งเวลากลับมาเองเพราะเริ่มตอนเว็บบูต
    - ถึงเวลา → สั่งรันสคริปต์ทั้งคลังที่ไม่ใช่ `ask-*`/`auto-*` (สคริปต์ที่ AI เขียนเองยังไม่มีคนตรวจ) ติดป้ายรอบ `nightly` = วันที่ไทยของเวลาที่ตั้ง (`ScriptRun.nightly`)
    - ไม่ซ้อนกัน: ถ้ายังมีรอบค้างอยู่ (รอบคืนก่อนไม่จบหรือคนสั่งรันเอง) จะไม่สั่งเพิ่ม รอและลองใหม่ทุก 30 วินาที จนเลยเวลาตั้งไป 180 นาที (`GRACE_MIN`) แล้วข้ามคืนนั้น
    - ไม่รันซ้ำวันเดียวกัน: จดคืนที่สั่งแล้วใน `runs/nightly.json` **ก่อน** สั่งรัน (เก็บ 30 คืน) รีสตาร์ทกลางคืนแล้วจึงไม่สั่งซ้ำ · รีสตาร์ทตอน deploy กลางวัน (เลยเวลาตั้งเกิน 180 นาที) ไม่ตามไปรันให้ · ถ้าตั้งเวลาข้ามเที่ยงคืน (เช่น 23:30) ตามรันได้หลัง 00:00 โดยใช้วันที่ของเวลาที่ตั้ง
    - ค่าเปิด/ปิดและเวลาเก็บใน `runs/nightly.json` (ต่างจากค่าตั้งอื่นที่อยู่ในหน่วยความจำ) ไฟล์นี้อยู่ใน `runs/` ที่ deploy ไม่ทับ
    - สรุปเช้า: จำนวนผ่าน/ล้ม/ผิดพลาด/ข้าม · รายการที่ล้มพร้อมเหตุผลขั้นที่พังและเลข ticket (หรือเหตุผลที่ไม่เปิด ticket) · เทียบกับคืนก่อนหน้าที่มีผลรัน: ล้มใหม่ / หายแล้ว / ล้มต่อเนื่อง · "ข้าม" = ตั้งใจรันแต่ไม่มีผลจบ (ผู้ใช้สั่งหยุด หรือคิวหายตอนเซิร์ฟเวอร์รีสตาร์ท) · อ่านได้ที่การ์ดบนหน้าหลัก, `GET /api/nightly[?date=YYYY-MM-DD]`, MCP `nightly {date?}`
    - ยังไม่ส่งสรุปไปที่อื่น (แชท/อีเมล) — ต้องให้ลุงจืดสั่งก่อน
    - ตัวตรวจ: `pnpm check:nightly` (`scripts/check-nightly.mjs`) ใช้เวลาปลอมกับ `startRuns` ปลอม ไม่รันสคริปต์จริง ตรวจว่า: สั่งครั้งเดียวตอนถึงเวลา, ไม่สั่งซ้ำหลังรีสตาร์ท, ปิดสวิตช์แล้วไม่สั่ง, ไม่ซ้อนกับรอบค้าง, ข้ามเที่ยงคืน และสรุปเทียบคืนก่อนถูกต้อง
12. ประวัติรอบถาวร · แนวโน้ม (`src/lib/run-history.ts`, `GET /api/history`, หน้า `/trends`)
    - ทุกรอบที่จบแล้วถูกจด 1 บรรทัดลง `data/run-history/YYYY-MM.jsonl` (เดือนตาม UTC ของเวลาจบ) — อยู่นอก `runs/` และเป็น append-only
    - เก็บเฉพาะที่ใช้วิเคราะห์: `id, scriptId, module, lens, bot, status, passed, failed, durationMs, startedAt, finishedAt, ticket, retestOf`
    - `durationMs` = ผลรวมเวลาของทุกขั้น (ไม่รวมเวลารอคิวและเปิดเบราว์เซอร์) · `ticket` = เลข issue ที่ระบบเปิดให้ ซึ่งได้ทีหลังรอบจบ จึงจดอีกบรรทัดของ id เดิม ตอนอ่านเอาบรรทัดท้ายสุดของแต่ละ id
    - จุดจดคือ `save()` ใน `src/lib/uat-runs.ts` (เรียก `recordRun` บรรทัดเดียว) · รอบที่ยังไม่จบข้าม · save ซ้ำโดยไม่มีอะไรเปลี่ยนไม่งอกบรรทัด
    - ตอนเริ่มเซิร์ฟเวอร์ (`src/instrumentation.ts`) เติมจาก `runs/*/run.json` เฉพาะรอบที่ยังไม่อยู่ในไฟล์ (id เดียวกันไม่เติมซ้ำ) แล้วลงบันทึกทำงาน `history-backfill`
    - หน้า `/trends` (ปุ่ม "แนวโน้ม" บนแถบบน) มี 3 ส่วน เลือกช่วง 7 / 30 / 90 วัน:
      - อัตราผ่านต่อโมดูลต่อวัน: แท่ง SVG ล้วน วันตามเวลาไทย นับเป็นจำนวนรอบ (รอบผิดพลาด/ถูกหยุดไม่นับ)
      - สคริปต์ที่ช้าลงผิดปกติ: ค่ากลางเวลารวมของ 3 รอบผ่านล่าสุด เทียบค่ากลางของรอบผ่านก่อนหน้า (สูงสุด 20 รอบ ต้องมีอย่างน้อย 5) ช้า ≥ 1.5 เท่า และเกิน 3 วิ — นับเฉพาะรอบที่ผ่าน เพราะรอบไม่ผ่านอาจค้างรอ timeout หรือจบเร็วเพราะขั้นหลังถูกข้าม
      - สคริปต์ที่ผลไม่นิ่ง: อย่างน้อย 4 รอบ สลับผ่าน↔ไม่ผ่าน ≥ 2 ครั้ง และ ≥ 30% ของรอบ · ไม่นับรอบตรวจซ้ำหลังแก้ (`retestOf`) เพราะไม่ผ่าน→ผ่านเป็นผลของการแก้ ไม่ใช่ความไม่นิ่ง
    - กติกาทั้งหมดอยู่ที่ `RULES` ใน `run-history.ts` และถูกส่งไปกับ API ให้หน้าเว็บอธิบายตรงกับที่ใช้จริง
    - กดชื่อสคริปต์หรือจุดสีเพื่อเปิดรอบนั้นที่หน้าหลัก (`/?run=<id>` เปิดรอบเก่าที่หลุดจาก 60 รอบล่าสุดได้ด้วย)

คัดลอก `.env.example` เป็น `.env.local` แล้วใส่ค่าจริง (`.env*.local` อยู่ใน `.gitignore` ห้าม commit)

| ตัวแปร | ใช้ทำอะไร |
|---|---|
| `ERP_TARGET_URL` | เว็บที่ทดสอบ ค่าเริ่มต้น `https://www.smlwork.com` (แก้ในหน้าตั้งค่าได้) |

|---|---|---|

| วิเคราะห์ก่อนเปิด issue | `mistral-large-4` | แยกชัดว่าส่วนไหนเดา · `deepseek-v4-pro` แต่งชื่อตารางที่ไม่มีจริง |
| ดูภาพหน้าจอ (`ui.see`, `ui.play`) | `kimi-k3` | ชี้พิกัดถูก 4/4 รุ่นอื่นชี้ไม่ได้ |
| งานเร็ว (เลือกบอท, Stagehand `ui.act`) | `deepseek-v4.1-flash` | ตอบ ~1–4 วิ |

สถานะสุขภาพ (`GET /api/health`, MCP `status`) ตรวจว่าทุกรุ่นมีใน Ollama Cloud

หน้าตั้งค่า (ไอคอนเฟือง) แก้ได้ 10 ค่า:
- เว็บ ERP
- รุ่น AI 4 งาน
- จำนวนรันพร้อมกัน
- ส่งเข้า IssueMate อัตโนมัติ
- เปิดหน้าต่าง Chrome ให้เห็น
- เปิดรอบกลางคืน (`nightlyEnabled`, ค่าเริ่มต้นปิด) และเวลาเริ่ม (`nightlyTime`, ค่าเริ่มต้น 02:00 เวลาไทย)

ค่าที่แก้อยู่ในหน่วยความจำ รีสตาร์ทแล้วกลับเป็นค่าจาก env — ยกเว้น 2 ค่าของรอบกลางคืนที่เก็บใน `runs/nightly.json`

ประวัติรอบถาวร: เก็บที่ `data/run-history/` (ไม่มี env ให้ตั้ง · อยู่ใน `.gitignore`) — deploy ต้องไม่ทับโฟลเดอร์นี้เหมือน `./runs` (tar ใส่ `--exclude=./data`) และควรสำรองไว้ เพราะเป็นแหล่งเดียวของแนวโน้มระยะยาว

## Dependency
- Node 22+ (เครื่องลุงจืด Node 24, เซิร์ฟเวอร์ Node 22), pnpm, Next.js 15, React 19, Tailwind 3, lucide-react
- Playwright + Chromium และ psql
- poppler-utils (`pdftotext`, `pdftoppm`) สำหรับขั้น `report.pdf` / `ui.pdf` — บน Ubuntu `apt-get install -y poppler-utils`
- บริการภายนอก:
  - Ollama Cloud (`https://ollama.com/api/chat`)
  - IssueMate MCP (`https://issue.dedezoom.com/mcp`)

## Usage example
รันแบบ production ที่พอร์ต 3050:
```bash
pnpm build
pnpm start -p 3050
```

ตรวจตรรกะรอบกลางคืน (ไม่รันสคริปต์จริง ไม่แตะเครือข่าย):
```bash
pnpm check:nightly
```

![หน้าคู่มือ /guide](docs/screens/05-guide.webp)

คู่มือสำหรับเพื่อนๆ อยู่ที่ `/guide` (`src/app/guide/page.tsx`) ใช้ภาพ Workflow 3 ภาพใน `public/guide/` — แก้ภาพที่ `docs/workflow/*.html` แล้วสร้างใหม่ (PNG + WebP, ต้องมี ffmpeg):
```bash
node docs/workflow/render.mjs
```

ตรวจตัวรันในเครื่องหลังแก้ `runner/run.mjs` (เปิดหน้า HTML ที่จงใจเหลื่อม/เปลี่ยนหน้าตาบน 127.0.0.1 ตรวจระนาบและเทียบภาพ 5 รอบ ไม่แตะ uat.smlwork.com/SML ต้องมี Playwright ตาม `UAT_PLAYWRIGHT`) — ผ่านจะพิมพ์ "ผ่านทั้งหมด":
```bash
node runner/selfcheck.mjs
```

สร้างทะเบียนเมนู `src/lib/erp-menus.json` ใหม่เมื่อเมนูใน ERP เปลี่ยน (รูปแบบ `[รหัส, ชื่อ, หมวด]`):
```bash
node -e "const m=require('D:/smlaiaccount/frontend/src/config/smlMenu.json'),o=[];const w=(n,g)=>{for(const x of n){const t=g||x.text;if(x.children?.length)w(x.children,t);else if((x.projects||[]).includes('SMLAccount'))o.push([x.name,x.text,t])}};w(m,'');require('fs').writeFileSync('src/lib/erp-menus.json',JSON.stringify(o));console.log(o.length)"
```

ดูบันทึกการทำงานวันนี้เฉพาะที่ล้ม (สรุป + รายการ) เพื่อหาจุดปรับปรุง:
```bash
curl -s "https://uat.smlwork.com/api/logs?errors=1&limit=20"
```

ดูแนวโน้ม 30 วัน (อัตราผ่านต่อโมดูลต่อวัน, สคริปต์ช้า, สคริปต์ไม่นิ่ง) และรันตัวตรวจของฟีเจอร์นี้บนเครื่อง (ใช้ไฟล์ปลอมในโฟลเดอร์ชั่วคราว ไม่แตะ `runs/` และไม่รันสคริปต์ทดสอบ):
```bash
curl -s "https://uat.smlwork.com/api/history?days=30"
pnpm check:history
```

รัน e2e ขายเชื่อ → รับชำระ ตรงจากตัวรัน (ต้องตั้ง `UAT_PG_*` ใน `.env.local`):
```bash
node runner/run.mjs --script uat-scripts/e2e-sale-credit-receipt.json --out runs/e2e-sale --base https://www.smlwork.com

ดูสรุปส่งมอบแบบ JSON:

รันสคริปต์เดียวจากบรรทัดคำสั่ง (ไม่ผ่านหน้าเว็บ):

```

ติดตั้งบนเซิร์ฟเวอร์ที่ใช้อยู่:
- โค้ดอยู่ `/opt/uat-tester`, ค่าลับอยู่ `/opt/uat-tester/.env.local` (สิทธิ์ 600)
- service `uat-tester` (systemd) ฟังที่ `127.0.0.1:3750` → `systemctl restart uat-tester`, `journalctl -u uat-tester -n 50`
- Caddy site `uat.smlwork.com` เปิดสาธารณะ (reverse proxy อย่างเดียว) — การกั้นคำสั่งอยู่ในแอป ดูข้อ 8 ใน Workflow
- เครื่องไม่มี psql: `bin/psql` เรียก psql ในคอนเทนเนอร์ `sml_postgresql`
- Playwright + Chromium อยู่ `/opt/uat-tester/pw` (`UAT_PLAYWRIGHT`, `PLAYWRIGHT_BROWSERS_PATH`)
- อัปเดตโค้ด: ส่งไฟล์ขึ้น `/opt/uat-tester` (ไม่ทับ `.env.local`, `./runs/`, `./baselines/` และ `./data/` ที่ราก — ถ้าใช้ tar ต้องเขียน `--exclude=./runs --exclude=./baselines --exclude=./data` ไม่งั้นจะตัด `src/app/api/runs` ทิ้งด้วย และภาพอ้างอิงถูกทับ) แล้ว `corepack pnpm@10.33.0 install --frozen-lockfile && corepack pnpm@10.33.0 build && systemctl restart uat-tester` (ต้องระบุ pnpm 10.33.0 เพราะ pnpm ที่ corepack ให้มาบนเซิร์ฟเวอร์เป็นรุ่น 12 ซึ่งปฏิเสธ lockfile)
- รีสตาร์ทตอนไม่มีรอบค้างเท่านั้น: เช็ก `GET /api/runs` ว่าไม่มี `running`/`queued` — service ใช้ `KillMode=control-group` รีสตาร์ทแล้วตัวรันที่ค้างถูกฆ่ากลางรอบ (เอกสาร `UAT-*` อาจค้างใน smldemo) · ค่าตั้งหน้าเว็บ/MCP `status settings` อยู่ในหน่วยความจำ รีสตาร์ทแล้วกลับเป็นค่าจาก env (`ISSUEMATE_AUTO`, `UAT_AUTO_SCRIPTS`, `UAT_AUTO_RETEST` …) ถ้าปิดส่ง IssueMate อัตโนมัติไว้ชั่วคราวต้องสั่งปิดซ้ำ

ตรวจตรรกะตรวจซ้ำอัตโนมัติด้วย IssueMate ปลอม (ไม่เรียกของจริง ไม่รันสคริปต์):
```bash
node --no-warnings src/lib/auto-retest.check.mjs
```

ขั้นที่ใช้ได้:
- หน้าจอ: `ui.goto`, `ui.demoLogin`, `ui.adminLogin` `{targetPath: "/admin/providers" | "/home"}`, `ui.openMenu`, `ui.click`, `ui.fill`, `ui.select`, `ui.press`, `ui.readText`, `ui.expectText`, `ui.expectVisible`, `ui.expectValue`, `ui.expectUrl`, `ui.expectClean` (ไม่มี HTTP/JS/console/DB error แฝง แล้ววัดระนาบ: ชิ้นในแถวเดียวกัน เช่น label/ช่องกรอก/ปุ่ม/ไอคอน/Badge กึ่งกลางแนวตั้งห่างกันเกิน 1px → ข้อค้นพบ S4 พร้อมภาพมีกรอบชี้จุด ไม่ทำให้ขั้นล้มและไม่เปิด issue อัตโนมัติ ดูรายละเอียดใต้ขั้นนั้นในหน้ารอบ · tool `runs` เห็นแค่จำนวนข้อค้นพบใน detail ของขั้น), `ui.screenshot` (เทียบกับภาพของรอบล่าสุดที่ผ่านของสคริปต์เดียวกัน: ไม่นับข้อความ/ค่าในช่องที่มีตัวเลข เช่นเลขเอกสาร วันที่ ยอด ทั้งของภาพนี้และภาพอ้างอิง · พิกเซลต่าง = สีห่างเกิน 40 จาก 255 · ต่างเกิน `UAT_VISUAL_DIFF_PCT` → ข้อค้นพบ S4 แนบภาพ diff: แดง = ต่าง, ฟ้า = ส่วนที่ไม่นับ · ขนาดภาพไม่เท่ากันก็แจ้ง · ไม่ทำให้ขั้นล้ม), `ui.pdf` `{selector, contains[]}` (กดปุ่มบนจอที่ดาวน์โหลด PDF เช่นปุ่มดาวน์โหลดในหน้าพิมพ์ แล้วตรวจข้อความในไฟล์แบบเดียวกับ `report.pdf`)
- AI กดเล่นหน้าจอ: `ui.act` `{instruction}` (Stagehand ทำ 1 อย่างตามคำสั่งภาษาไทย), `ui.see` `{expect}` (AI ดูภาพแล้วตัดสินผ่าน/ไม่ผ่าน), `ui.play` `{goal, maxSteps}` (Computer Use: AI ดูจอ คลิก พิมพ์ จนครบเป้าหมาย สิ่งผิดปกติที่ AI เห็น = ขั้นไม่ผ่าน บันทึกเอกสารทดสอบได้โดยใส่ `{{run.tag}}`) · ผลจาก AI ต้องให้คนยืนยันก่อนแก้
- API: `api.request`
- รายงาน PDF: `report.pdf` `{body, contains[]}` — ขอ PDF แบบที่ผู้ใช้กดพิมพ์รายงาน (`POST /api/process/report/pdf` ใช้ body เดียวกับ `/api/process/report/run`) แล้วหาทุกค่าใน `contains` จากข้อความในไฟล์ · หลักฐาน = ภาพหน้าแรก + ไฟล์ PDF (ปุ่ม "เปิด PDF รายงาน" ในไทม์ไลน์) · ภาพหน้าแรกเทียบกับรอบล่าสุดที่ผ่านแบบเดียวกับ `ui.screenshot` แต่ใช้เกณฑ์ % อย่างเดียว (ผูกกับชื่อขั้น)
- ฐานข้อมูล: `db.query` (อ่านอย่างเดียว), `db.exec` (เขียน — ใช้กับข้อมูลที่ขึ้นต้นด้วย UAT) · ใส่ `database` ได้ 3 ฐานทดสอบ (ดูข้อ 9 ใน Workflow)
- อื่น ๆ: `wait`, `set`

ตัวเทียบค่าที่ใช้ได้: `eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `contains`, `matches`, `exists`, `empty`, `same`

ถ้าไม่ใส่ `lens` ระบบเลือกให้เอง: มีขั้น `db.*` = data, ไม่มี = screen

## Limitation
- เทียบภาพ (`ui.screenshot`/PDF): ภาพอ้างอิงเขียนทับทุกรอบที่ผ่าน จึงแจ้งหน้าตาเปลี่ยนแค่รอบแรกที่เห็น (รอบไม่ผ่านไม่เขียนทับ) · PDF ไม่มี DOM จึงไม่ปิดตัวเลข เลขเอกสาร/ยอดที่เปลี่ยนทุกรอบอาศัยเกณฑ์ % · ส่วนที่เปลี่ยนเองแต่ไม่มีตัวเลข (กราฟ canvas, toast, ภาพสุ่ม) ไม่ถูกปิด อาจแจ้งเกิน · ขั้นที่เปลี่ยนชื่อภาพ/ชื่อขั้นเริ่มภาพอ้างอิงใหม่ ภาพเก่าไม่ถูกลบ · ยังไม่ได้ทดสอบเส้นทาง PDF ในเครื่อง Windows (ไม่มี `pdftoppm`)
- ตรวจระนาบ (`ui.expectClean`) ดูเฉพาะแถวที่สูงไม่เกิน 64px และข้ามกลุ่มที่วางซ้อนบน-ล่าง · ข้อความที่จัดตรงแล้วยังห่างกึ่งกลางช่องกรอก ~0.5px ตามเมตริกฟอนต์ จึงเลื่อน 1px วัดได้ ~1.5px และถูกแจ้ง · ฟอนต์ต่างขนาดในแถวเดียวกันวัดด้วยกึ่งกลาง ไม่ใช่เส้นฐานตัวอักษร · แถวเดิมแจ้งครั้งเดียวต่อรอบ (สูงสุด 8 แถวต่อครั้ง)
- `report.pdf` ตรวจว่ามีข้อความ ไม่ตรวจตำแหน่งคอลัมน์ · วรรณยุกต์ไทยบางตัวใน PDF ของ ERP เป็นอักษร private-use (U+F70A–F70F) คำไทยจึงหาไม่เจอ ให้ใส่เลขเอกสาร/ตัวเลขใน `contains`
